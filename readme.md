# Voice Interview JP

일본 IT 기업 취업을 준비하는 한국인 지원자를 위한 **완전 무료(0원) 음성 모의 면접 트레이너**.

> 이 문서는 `OT.txt`(초기 기획 메모)를 참고하여 다시 정리한 기획안입니다. 무료 배포·무료 운영을 최우선 원칙으로 삼고, 이 원칙과 충돌하는 기능(특히 유료 API가 필요한 AI 첨삭/AI 꼬리질문)은 전부 제외했습니다.

---

## 1. 목적 및 핵심 원칙

- **목적**: 일본어 음성으로 질문을 듣고, 일본어로 말하며 답변하는 모의 면접을 브라우저에서 무료로 반복 연습.
- **0원 운영 원칙 (최우선)**
  - **유료로 전환될 수 있는 요소는 처음부터 설계에 넣지 않는다.** (LLM API, 유료 STT/TTS API, 유료 DB 플랜 등)
  - 모든 AI/음성 처리는 브라우저 내장 **Web Speech API**로만 처리 (서버 호출 없음 → 토큰 과금 없음).
  - 데이터 저장은 **Supabase 무료 티어** 한도 안에서만 사용.
  - 배포는 **Vercel 무료 티어(Hobby)** 로 고정.
  - "꼬리 질문(follow-up question)" 기능은 원한다고 했지만, **AI가 답변을 이해해서 생성하는 방식은 유료 API가 필요하므로 채택하지 않는다.** 대신 아래 4-2절처럼 **사전에 정의된 꼬리 질문 세트 + 규칙 기반(키워드) 매칭**으로 "꼬리질문을 받는 느낌"을 무료로 구현한다.

---

## 2. 기술 스택 (100% 무료 티어)

| 영역 | 선택 | 비고 |
|---|---|---|
| 프런트엔드 | Next.js (App Router) | Vercel과 궁합이 가장 좋음 |
| 배포/호스팅 | **Vercel Hobby (무료)** | Git 연동 자동 배포, 서버리스 함수 무료 한도 내 사용 |
| 백엔드/DB | **Supabase Free Tier** | PostgreSQL DB, Auth, Storage 포함 |
| 인증 | Supabase Auth (무료) | 이메일 또는 소셜 로그인, 월 5만 MAU까지 무료 |
| 음성 인식(STT) | 브라우저 `Web Speech API` (`SpeechRecognition`) | 서버 호출 없음, ja-JP 실시간 타이핑 |
| 음성 합성(TTS) | 브라우저 `Web Speech API` (`SpeechSynthesis`) | 서버 호출 없음, 질문 낭독 |
| 음성 파일 저장(선택) | Supabase Storage 무료 1GB | 필요할 때만 사용, 기본은 텍스트 로그만 저장 |

**의도적으로 배제한 것**: OpenAI/Gemini 등 LLM API, 유료 클라우드 STT(Google/Naver Clova 등), 유료 TTS API, Vercel/Supabase 유료 플랜 승급이 필요한 기능 전부.

## 3. Supabase 무료 티어 한도와 설계 대응

Supabase 무료 프로젝트는 다음 한도를 가지므로, 이 한도 안에서 동작하도록 설계한다.

- DB 500MB, Storage 1GB, 월간 Auth MAU 5만 — 개인/소규모 다중 사용자 용도로는 충분.
- **7일 이상 미접속 시 프로젝트가 일시 정지(pause)** 될 수 있음 → README/운영 노트에 "가끔 접속해서 깨워주기" 안내 문구 명시, 또는 무료 크론(GitHub Actions 등)으로 주기적 핑(ping) 고려.
- 음성 녹음 파일(.webm) 저장은 **기본 비활성화(옵트인)** — 텍스트 로그만 저장해도 복습 목적은 충분히 달성되며 Storage 용량 소진을 방지.

## 4. 주요 기능

### 4-1. 동적 질문 출제 시스템 (Supabase 연동)

- 카테고리: 기본 인성(자기PR/지원동기), 기술/프로젝트 경험, 컬처핏, 역질문 등.
- 난이도/카테고리별 랜덤 세트 조합 (5~10문항).
- 사용자가 목표 기업 JD/이력서에 맞춘 **커스텀 질문 추가/수정/삭제**.
- 질문 한국어 번역 토글, 다시 듣기(TTS) 버튼.

### 4-2. 꼬리 질문(Follow-up) 기능 — **무료·규칙 기반**

AI 없이도 "면접관이 이어서 파고드는" 느낌을 주기 위한 3단계 설계:

1. **정적 꼬리질문 세트 (기본)**
   각 질문(`questions`)마다 미리 작성된 꼬리질문 1~3개를 DB에 연결(`follow_up_questions`). 답변 종료 후 정해진 순서 또는 랜덤으로 1개를 이어서 제시.
   예) "팀 프로젝트 경험은?" → (꼬리) "그 프로젝트에서 가장 어려웠던 순간은?"

2. **키워드 기반 매칭 (선택 고도화)**
   STT로 받은 답변 텍스트에 특정 키워드(예: "チーム", "エラー", "納期")가 등장하면, 그 키워드에 매핑된 꼬리질문을 선택. 서버 호출·AI 호출 없이 클라이언트 자바스크립트의 단순 문자열 매칭으로 처리 → 비용 0원.

3. **사용자 커스텀 꼬리질문**
   사용자가 자신의 커스텀 질문에 원하는 꼬리질문을 직접 입력해 등록 가능.

> ⚠️ 답변 내용을 실제로 "이해"하고 새로운 질문을 생성하는 AI 꼬리질문은 LLM API 비용이 발생하므로 **본 버전에서는 제외**. 향후 별도 유료 플랜/기능으로 검토 가능하나 현재 기획 범위 밖.

### 4-3. 실시간 일본어 음성 인터페이스

- 마이크 입력 시작 → 사용자의 일본어 발화를 화면에 실시간 스트리밍 타이핑.
- 인식 결과를 눈으로 즉시 확인해 발음/인식 정확도 자가 점검.
- 제한 시간 타이머(1분/2분), 인식된 텍스트 수동 보정(typo 수정) 가능.

### 4-4. 면접 세션 기록 & 복습 대시보드

- 면접 종료 시 질문-꼬리질문-답변 전체 로그를 Supabase DB에 자동 저장.
- 마이페이지에서 날짜별 세션 열람, 텍스트 스크립트 복사, Markdown 다운로드.

## 5. 데이터 모델 (개략)

```
users              (Supabase Auth 기본 제공)

questions
  id, category, difficulty, text_ja, text_ko,
  is_custom, owner_user_id, created_at

follow_up_questions
  id, parent_question_id (FK -> questions.id),
  text_ja, text_ko, trigger_keywords (text[] , nullable),
  order_index

sessions
  id, user_id, mode(basic|technical|custom), created_at

session_answers
  id, session_id (FK), question_id (FK),
  follow_up_question_id (FK, nullable),
  answer_text, audio_url (nullable), answered_at
```

- Row Level Security(RLS)로 사용자별 데이터 접근 제한 (Supabase 무료 티어에서도 기본 제공).

---

## 6. 사용자 흐름 (User Flow)

1. **모드 선택**: 기본 면접 / 기술 면접 / 커스텀 질문 세트.
2. **질문 제시**: 화면에 일본어 질문 표시 + TTS로 낭독.
3. **음성 답변**: 사용자가 일본어로 답변 → STT로 실시간 자동 타이핑.
4. **꼬리 질문(조건부)**: 사전 정의/키워드 매칭된 꼬리질문이 있으면 이어서 제시 → 재답변.
5. **다음 질문**: 세션 진행(5~10문항, 꼬리질문 포함).
6. **결과 저장**: 전체 로그를 Supabase에 저장하고 세션 리포트 확인.

## 필수 업그레이드

### 1. “면접 모드”를 더 현실적으로 세분화

현재의 기본/기술/커스텀 모드는 유지하되, 실제 사용 상황에 맞게 아래 모드를 추가하세요.

| 모드 | 구성 | 사용자 가치 |
|---|---|---|
| 연습 모드 | 질문 확인, 다시 듣기, 자막 확인, 시간 무제한 | 일본어 초중급 사용자의 부담 감소 |
| 실전 모드 | 질문 미리 보기 금지, 질문 1회 낭독, 제한 시간, 답변 수정은 종료 후에만 | 실제 면접 긴장감 재현 |
| 약점 보완 모드 | 과거 세션의 짧은 답변·반복 표현·빈약한 카테고리만 재출제 | 반복 연습의 효율 향상 |
| 모의 1차 면접 | 자기소개 → 지원동기 → 강점/약점 → 경험 → 역질문 | 일본 기업 면접의 기본 흐름 훈련 |
| 기술 면접 | 프로젝트 설명 → 역할 → 기술 선택 이유 → 문제 해결 → 성과·회고 | 데이터사이언스·IT 직무 포트폴리오 연결 |
| 압박 꼬리질문 모드 | 같은 주제에 2~3회 연속 후속 질문 | “왜?”, “구체적으로?”, “본인의 기여는?” 대응 훈련 |
| 逆質問 모드 | 면접 종료 직전 역질문만 집중 훈련 | 일본 취업에서 실전 활용도 높음 |

특히 사용자가 일본 IT 기업 취업을 준비한다는 맥락에서는, 단순 질문 랜덤 출제보다 **면접의 순서와 맥락을 가진 시나리오 기반 세션**이 훨씬 중요합니다. 예를 들어 데이터 분석 프로젝트를 이야기한 뒤 “당신의 역할은 무엇이었습니까?”, “그 지표를 선택한 이유는 무엇입니까?”, “실패 또는 한계는 무엇이었습니까?”로 이어지는 구조가 좋습니다.

### 2. AI 없이 “규칙 기반 면접 피드백 엔진” 추가

이 프로젝트의 가장 큰 업그레이드 포인트입니다. LLM 첨삭 없이도 사용자가 매번 개선할 수 있도록 **측정 가능한 피드백**을 제공하세요.

#### 답변별 기본 지표

- 답변 시간: 목표 시간 대비 너무 짧거나 긴지 표시
- 글자 수 및 추정 일본어 발화량
- 문장 수
- 필러 사용 횟수: `えー`, `あの`, `その`, `えっと`, `まあ`, `なんというか`
- 반복 표현: 같은 단어·어미·접속사 반복 감지
- 결론 선행 여부: 첫 1~2문장에 `結論から申し上げますと`, `私の強みは`, `志望理由は` 등이 있는지
- 구체성 신호: 숫자, 기간, 팀 규모, 역할, 도구명, 결과가 포함되었는지
- 구조 신호: `結論 → 理由 → 具体例 → 結果 → 学び` 또는 STAR 구조가 있는지
- 일본 취업 면접 표현: 겸양 표현, 정중체, 연결 표현 사용 여부

예를 들어 아래처럼 보여줄 수 있습니다.

| 항목 | 결과 예시 | 해석 |
|---|---:|---|
| 답변 시간 | 38초 / 목표 60~90초 | 핵심 근거 또는 사례를 더 추가 |
| 필러 | 9회 | `えー`, `あの` 사용이 다소 많음 |
| 수치·결과 | 0개 | 프로젝트 성과를 숫자로 보강 |
| STAR 구조 | 2/4 충족 | 행동(Action)과 결과(Result)를 명확히 제시 |
| 결론 선행 | 미충족 | 첫 문장에 답을 먼저 말하는 연습 권장 |
| 기술 키워드 | Python, KoBERT | 좋음. 데이터셋·역할·평가지표도 추가 권장 |

이 기능은 STT 텍스트에 대한 정규식, 사전, 문자열 비교, 단순 점수 규칙만으로 구현할 수 있습니다. 즉 서버 LLM 호출 없이도 “다음 회차에서 무엇을 고칠지”를 알려주는 제품이 됩니다.

#### 점수 대신 “훈련 신호”를 쓰는 이유

초기에는 총점 82점 같은 단일 점수를 전면에 내세우지 않는 편이 좋습니다. STT 오인식이 일본어 능력 점수처럼 보일 위험이 있기 때문입니다. 대신 다음처럼 표현하세요.

- 개선 우선순위: **구체적 성과 제시**
- 유지할 점: 결론을 먼저 제시함
- 다음 답변 목표: 60초 이상 + 숫자 1개 + 본인 역할 1개
- 추천 꼬리질문: “その成果を測定した指標は何ですか。”

이 방식은 사용자를 평가하는 서비스가 아니라, **반복 연습을 돕는 트레이너**라는 서비스 정체성에도 더 잘 맞습니다.

### 3. 키워드 꼬리질문 엔진을 “규칙 그래프”로 확장

현 기획의 키워드 매칭은 좋지만, 단순 포함 여부만으로는 질문이 부자연스러울 수 있습니다. 기존 방식을 유지하면서 아래 필드를 추가하세요.

```text
follow_up_rules
  id
  parent_question_id
  trigger_type          -- keyword | missing_keyword | answer_length | order | random
  trigger_value         -- ["チーム", "協力"], 60, ["数値", "成果"] 등
  priority              -- 우선순위
  cooldown_count        -- 동일 규칙 재사용 방지
  follow_up_question_id
  feedback_hint_ko
  feedback_hint_ja
```

#### 추천 규칙 유형

| 규칙 | 예시 | 연결 꼬리질문 |
|---|---|---|
| 키워드 포함 | `チーム`, `協力` 등장 | “チーム内でのあなた自身の役割は何でしたか。” |
| 기술 용어 포함 | `Python`, `SQL`, `KoBERT` 등장 | “その技術を選定した理由を教えてください。” |
| 성과 키워드 부재 | 숫자·결과 표현이 전혀 없음 | “成果をどのような指標で測定しましたか。” |
| 답변이 지나치게 짧음 | 20초 미만 또는 글자 수 기준 미달 | “もう少し具体的な例を挙げていただけますか。” |
| 역할 언급 부재 | `私が担当した`, `役割`, `担当` 부재 | “その中で、あなたが担当した部分は何ですか。” |
| 실패·한계 언급 | `失敗`, `課題`, `エラー` 등장 | “その課題をどのように解決しましたか。” |
| 순차 심화 | 첫 꼬리질문에 답변 완료 | “その経験から学んだことは何ですか。” |

이 구조의 장점은 “AI처럼 보이기 위해 무리하게 생성”하지 않고도, **면접의 논리적 깊이**를 단계적으로 구현한다는 점입니다.

### 4. 답변 템플릿 코치 추가

일본 IT 취업 면접은 답변의 형식이 중요합니다. 질문을 들은 뒤 말문이 막히는 문제를 줄이기 위해, 답변 화면에 선택형 가이드만 제공하세요.

#### 추천 템플릿

| 질문 유형 | 화면 가이드 |
|---|---|
| 자기소개 | 현재 상태 → 전공/강점 → 대표 경험 → 지원 방향 |
| 지원동기 | 결론 → 기업의 매력 → 본인 경험과 연결 → 입사 후 기여 |
| 프로젝트 | 목적 → 본인 역할 → 사용 기술 → 문제/해결 → 결과/배운 점 |
| 강점 | 강점 → 근거 경험 → 업무 적용 방식 |
| 약점 | 약점 → 개선 행동 → 현재 변화 |
| 실패 경험 | 상황 → 문제 → 행동 → 결과 → 배운 점 |
| 역질문 | 기업 이해를 보여주는 질문 → 입사 후 성장·기여와 연결 |

실전 모드에서는 템플릿을 숨기고, 연습 모드에서만 “힌트 보기”로 표시하면 됩니다. 사용자가 스스로 문장을 만들되, 답변의 골격을 반복 학습할 수 있습니다.

### 5. 질문 품질 시스템 추가

서비스 품질은 STT보다도 결국 **질문 데이터 품질**에 크게 좌우됩니다. `questions` 테이블에 다음 속성을 추가하는 것을 권장합니다.

```text
questions
  id
  category
  difficulty
  text_ja
  text_ko
  company_stage          -- HR | 1st_interview | technical | final
  job_family             -- frontend | backend | data | AI_ML | common
  expected_duration_sec  -- 30 | 60 | 90 | 120
  answer_framework       -- PREP | STAR | project | motivation
  evaluation_points      -- text[] 또는 jsonb
  tags                   -- text[]
  is_custom
  owner_user_id
  created_at
```

#### 데이터사이언스·AI 직무용 태그 예시

- `Python`
- `SQL`
- `R`
- `data_preprocessing`
- `EDA`
- `machine_learning`
- `NLP`
- `KoBERT`
- `model_evaluation`
- `team_project`
- `GitHub`
- `Streamlit`
- `problem_solving`
- `business_impact`

이렇게 하면 사용자는 단순히 “기술 면접”을 선택하는 수준을 넘어서, 예를 들어 **“Python + 데이터 전처리 + 프로젝트 경험 + 1차 면접”**이라는 질문 세트를 만들 수 있습니다.

## 신뢰성·개인정보 업그레이드

### STT 지원 감지와 이중 폴백

`SpeechRecognition`은 모든 브라우저에서 동일하게 동작하지 않습니다. 따라서 첫 진입 시 기능을 검사하고, 지원되지 않을 때도 서비스 전체가 막히지 않도록 해야 합니다. Web Speech API는 음성 인식과 음성 합성으로 구성되며, 음성 인식 지원과 동작은 브라우저별로 차이가 있습니다. [developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API)

권장 UX는 다음과 같습니다.

1. 지원 여부 확인: `SpeechRecognition` 또는 `webkitSpeechRecognition`
2. 일본어 `ja-JP` 설정 가능 여부 확인
3. 음성 인식 미지원 시 “텍스트 면접 모드”로 자동 전환
4. 마이크 권한 거부 시 “답변 직접 입력” 제공
5. 음성 합성 음성 목록에서 일본어 음성이 없으면 질문 텍스트만 표시
6. 인터넷·STT 오류 발생 시 현재 누적 답변을 로컬에 임시 보존

이렇게 하면 Chrome/Edge가 아닌 환경에서도 “서비스 사용 불가”가 아니라 **음성 기능 일부 제한**으로 처리할 수 있습니다.

### 개인정보 고지 수정

기획 문서에는 아래처럼 표현하는 편이 정확합니다.

> 본 서비스는 별도의 유료 STT API 키나 자체 음성 처리 서버를 사용하지 않습니다. 다만 브라우저의 음성 인식 기능은 브라우저·운영체제·설정에 따라 외부 서버 기반으로 처리될 수 있습니다. 사용자는 음성 녹음 저장 여부를 직접 선택할 수 있으며, 기본값은 텍스트 로그 저장입니다.

MDN 문서상 기본 Web Speech 음성 인식은 서버 기반 엔진을 사용할 수 있고, 이 경우 음성은 웹 서비스로 보내져 처리될 수 있습니다. 반면 브라우저가 지원할 경우 로컬 처리 옵션과 언어 팩을 통해 외부 전송 없이 인식하도록 구성할 수 있습니다. [developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API)

### 녹음 저장 개선

음성 저장 기능은 유지하되 다음 정책을 적용하세요.

- 기본값: 저장 안 함
- 사용자 선택: “이번 세션만 저장” 또는 “항상 저장”
- 세션별 삭제 버튼
- 전체 음성 파일 삭제 버튼
- 자동 만료: 예를 들어 7일 또는 30일 후 자동 삭제를 사용자가 선택
- 업로드 전 파일 크기와 남은 저장 공간 안내
- 오디오 다운로드 지원
- Safari와 Chromium 계열의 녹음 포맷 차이를 고려해 MIME 타입을 감지

`MediaRecorder`는 현대 브라우저에서 폭넓게 지원되는 API이지만, 브라우저별 지원 코덱은 다를 수 있습니다. 따라서 `audio/webm`을 고정하지 말고 `MediaRecorder.isTypeSupported()`로 지원 포맷을 찾아야 합니다. [developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/MediaRecorder?from_column=20423&from=20423)

## 무료 운영 원칙 재설계

### “0원”의 정의를 더 정확히

현재 설계는 **API 사용량 기반의 직접 비용 0원**을 잘 달성합니다. 다만 “어떤 규모에서도 0원”은 보장할 수 없습니다.

| 항목 | 현재 판단 | 개선된 문구 |
|---|---|---|
| Web Speech API | 별도 API 키·토큰 비용 없음 | 브라우저 정책·네트워크·지원 여부에 의존 |
| Supabase | 소규모 사용에 적합 | 무료 한도 내에서만 0원 |
| Vercel Hobby | 포트폴리오·개인 프로젝트에 적합 | 개인·비상업 용도로 사용 |
| 음성 파일 | 옵트인으로 비용 위험 축소 | 파일 저장은 가장 먼저 한도에 도달할 수 있음 |
| 공개 서비스 | 무료 사용 가능성이 있음 | 상업화·대규모 트래픽은 별도 호스팅 정책 검토 필요 |

Supabase Free는 스토리지 1GB를 제공하며, 무료 프로젝트는 낮은 활동 상태가 7일 지속되면 일시 정지될 수 있습니다. 따라서 텍스트 중심 저장, 음성 옵트인, 만료 정책, 상태 안내 UI가 필수입니다. [supabase](https://supabase.com/docs/guides/platform/free-project-pausing)

또한 Vercel Hobby는 무료이지만 공식적으로 개인·비상업적 사용을 대상으로 합니다. 따라서 지금은 “개인 포트폴리오 및 비상업적 공개 데모”라는 위치를 명확히 하고, 향후 유료 기능·광고·기업 B2B 제공을 시작할 때 호스팅 정책을 재검토해야 합니다. [vercel](https://vercel.com/docs/plans/hobby)

### 자동 정지 대응은 “유지용 핑”보다 UX 우선

GitHub Actions로 주기적 ping을 보내는 방식은 기술적으로 가능하지만, 서비스의 실제 사용자 활동이 없는 상황에서 무료 티어의 휴면 정책을 우회하려는 운영 방식으로 볼 여지도 있습니다. 더 건전한 접근은 다음입니다.

- 개인 포트폴리오라면: 정지 가능성을 README와 앱 안내에 명시
- 재개 중이면: “데이터베이스가 절전 상태에서 깨어나는 중입니다. 잠시 후 다시 시도해 주세요.” 화면 제공
- 공개 운영이 필요해지면: 해당 시점에 유료 플랜 또는 다른 배포/DB 전략을 결정
- 중요한 데이터라면: Markdown/JSON 내보내기와 사용자 로컬 백업을 기본 제공

특히 `stt_raw_text`와 `corrected_answer_text`를 분리해 두세요. 이것은 음성 인식의 한계를 사용자가 교정한 결과와 구분해 복습할 수 있게 하고, 향후 “자주 오인식된 기술 용어”를 사용자 개인 사전에 추가하는 근거가 됩니다.

### 1. 사용자 발화 품질 분석 고도화 (정규식/사전 기반)

별도의 LLM 호출 없이 클라이언트 사이드 문자열 파싱과 정규식 엔진만으로 즉시 적용 가능한 세부 규칙입니다.

* **비즈니스 일본어 경어/정중체 일관성 검사:**
* **데스/마스체 vs 보통체 혼용 감지:** 발화 내 `だ / である / だから` 등 보통체 어미와 `です / ます / ございます` 정중체 어미가 한 답변 내에 섞여 있는지 탐지하여 "문말 어미 통일(です・ます調)" 피드백 제공.
* **쿠션어(クッション言葉) 사용 여부:** `恐れ入りますが`, `差し支えなければ`, `恐縮ですが` 등 완곡 표현의 포함 여부 체크.
* **비즈니스 겸양/존경 표현:** `御社(おんしゃ)` / `貴社(きしゃ)` 구분(면접 발화 시에는 `御社`가 원칙), `拝見する`, `伺う`, `申す` 등 올바른 겸양어 사용 가이드.


* **STT 기술 용어 사전(Custom Phonetic Dictionary) 매핑:**
* 일본어 STT 엔진 특성상 한국어/영어 IT 용어가 카타카나나 엉뚱한 한자로 변환되는 현상 자동 보정.
* *예시 매핑 테이블:* `パイソン` $\rightarrow$ `Python`, `シーケル/エスキューエル` $\rightarrow$ `SQL`, `コベルト` $\rightarrow$ `KoBERT`, `ギットハブ` $\rightarrow$ `GitHub`.
* STT 원문(`stt_raw_text`)을 사용자에게 보여줄 때 자동 치환 추천 태그를 띄워 원클릭 수정 지원.

## 기술적으로 검증된 부분

**응답 지연 측정**은 실제로 `SpeechRecognition`이 제공하는 `onsoundstart`, `onspeechstart`, `onspeechend` 이벤트로 구현 가능합니다. `onsoundstart`는 인식 가능 여부와 무관하게 소리가 감지된 시점, `onspeechstart`는 그 소리가 음성으로 인식된 시점을 알려주므로, 질문 TTS 종료 시각과 `onspeechstart` 발생 시각의 차이를 계산하면 "응답 지연 시간"을 정확히 측정할 수 있습니다. [developer.mozilla](https://developer.mozilla.org/fr/docs/Web/API/SpeechRecognition)

**음성 파형 시각화**도 표준적인 구현입니다. `AudioContext.createAnalyser()`로 `AnalyserNode`를 만들고 마이크 스트림을 연결한 뒤, `getByteTimeDomainData()`나 `getByteFrequencyData()`로 데이터를 뽑아 캔버스에 그리는 방식은 MDN 공식 문서에 나온 표준 패턴이며 서버 호출이 전혀 없습니다. [developer.mozilla](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)

## 재검토가 필요한 부분

### 1. `pg_cron` 기반 TTL 자동 삭제는 free tier에서 신뢰도가 낮음

이 부분은 출처 간 정보가 엇갈립니다. 일부 자료는 "pg_cron이 모든 플랜(무료 포함)에서 기본 제공된다"고 하지만, 다른 분석은 "pg_cron은 장시간 실행되는 백그라운드 워커가 필요해 Pro 이상에서만 사용 가능하다"고 설명합니다.  더 중요한 문제는 두 주장이 모두 맞더라도 실무적으로는 무의미하다는 점입니다. **무료 프로젝트가 7일간 비활성 상태이면 프로젝트 자체가 일시 정지되고, 이때 pg_cron을 포함한 모든 예약 작업이 함께 멈춥니다.**  즉, "음성 파일 30일 후 자동 삭제"를 pg_cron에 맡기면, 정작 사용자가 오래 쉬었다가 돌아왔을 때 삭제가 실행되지 않았거나 밀려서 실행될 수 있습니다. [crontap](https://crontap.com/guides/supabase-cron-jobs)

**개선안**: TTL 삭제는 DB 크론이 아니라 **클라이언트 진입 시점에 확인하는 방식**으로 바꾸세요. 사용자가 로그인하거나 마이페이지에 접속할 때, `created_at + retention_days < now()`인 오디오 레코드를 찾아 그 자리에서 삭제 요청을 보내는 방식입니다. 이렇게 하면 프로젝트 휴면 여부와 무관하게 항상 정확히 동작하고, 별도 확장 설치나 크론 설정도 필요 없습니다.

### 2. "Web Worker에서 서버 연산 부하 0화"라는 표현은 정정 필요

원문의 "서버 사이드 LLM/STT API 의존 제거"는 정확하지만, "발화 텍스트 분석 로직을 Web Worker로 구현해 서버 연산 부하를 0화한다"는 표현은 다소 과장입니다. 정규식·사전 매칭 수준의 연산은 애초에 메인 스레드에서 처리해도 UI가 끊기지 않을 만큼 가볍습니다. Web Worker 도입은 "서버 부하 감소"가 아니라 "브라우저 메인 스레드 부하 분리"이므로, 포트폴리오 문서에는 **"서버 의존 제거"와 "클라이언트 성능 최적화"를 별개 항목으로 구분**해서 쓰는 것이 기술적으로 더 정확합니다.

### 3. `politeness_score_ratio`는 정밀 점수가 아니라 참고 지표로 표기

정중체 비율을 0.00~1.00처럼 소수점 두 자리 수치로 제시하면 마치 정밀 측정값처럼 보이지만, 실제로는 문말 어미 패턴 매칭 기반의 근사치입니다. 특히 일본어는 문장 경계 인식이 STT 텍스트에서 불완전할 수 있어 오차가 생기기 쉽습니다. DB 필드명과 값 자체는 유지하되, UI에는 "정중체 일관성: 약 82% (문말 어미 기준 추정치)"처럼 **추정치임을 명시**하는 문구를 붙이는 것이 신뢰도 면에서 안전합니다.

### 4. STT 오인식 보정 사전은 이 프로젝트의 핵심 차별화 포인트

`user_custom_terms` 테이블 설계는 특히 훌륭합니다. Web Speech API 기반 STT는 브라우저에 따라 서버 기반 인식 엔진을 쓸 수 있고 , 이 과정에서 고유명사·기술 용어의 오인식이 잦다는 점은 이미 확인된 한계입니다. 이를 결점으로 두지 않고 "사용자가 직접 사전을 채워나가는 개인화 루프"로 전환한 설계는, 데이터사이언스 전공자이자 일본 IT 취업 준비생이라는 사용자 배경과도 맞아떨어집니다. `パイソン → Python`, `コベルト → KoBERT` 같은 매핑은 실제 면접에서 반복적으로 나올 용어이므로 초기 사전에 미리 20~30개를 채워두고 배포하는 것을 권장합니다.
