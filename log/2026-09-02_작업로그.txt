  시 닫힘(JS로 클릭 이벤트 발생시켜 확인), 하단 컨트롤 줄바꿈까지 전부 정상 동작 확인.

[1. VOICEVOX 목소리가 가끔만 나오고 대부분 무음으로 바로 답변 단계로 넘어가던 버그]
"波音リツ만 가끔 나오고 다른 목소리는 아예 안 나오거나 바로 답변으로 넘어간다" 제보로
확인했습니다. 예상대로 어제 경고했던 대로였습니다 — tts.quest의 키리스(무료, 비공식)
경로가 요청 제한에 자주 걸려 합성이 실패하는데, 실패 시 그냥 onEnd()만 호출하고 아무
소리도 내지 않은 채 다음 단계로 넘어가던 것이 원인이었습니다.
수정: features/interview/hooks/useSpeechSynthesis.ts에서 VOICEVOX 합성/재생이 실패하면
(요청 실패, 타임아웃, 자동재생 차단 등) 무음으로 넘어가는 대신 브라우저 기본 음성
(speakNative)으로 자동 대체하도록 했습니다. 이제 어떤 경우든 질문이 최소한 무슨 목소리로든
들리고, 화면이 그냥 답변 단계로 건너뛰는 일은 없습니다. (다만 VOICEVOX 자체의 불안정성은
외부 서비스 한계라 근본적으로 없앨 수는 없고, 이 폴백으로 사용자 경험만 보정한 것입니다.)

[2. "질문 X / Y" 표시가 꼬리질문을 전혀 세지 않던 버그 발견 및 수정]
"질문이 아직 18개로 나오는데, 소분류 질문이랑 꼬리질문 모두 합한 개수를 세어달라"는
요청으로 코드를 다시 보니 실제 버그를 발견했습니다: features/interview/hooks/
useInterviewMachine.ts가 꼬리질문을 결정하면 currentQuestion만 바꾸고 questions 배열과
queueIndex는 전혀 건드리지 않고 있었습니다 — 즉 꼬리질문이 몇 개가 이어지든 화면 상단의
"질문 X / Y"는 전혀 늘어나지 않고 멈춰 있었습니다.
수정: 꼬리질문이 결정되면 그 질문을 questions 배열의 현재 위치 바로 다음에 실제로
끼워넣고(splice) queueIndex도 함께 한 칸 전진시키도록 했습니다. 이제 꼬리질문이 나올
때마다 Y(전체 개수)가 실제로 늘어나고 X(현재 위치)도 같이 올라가서, 대분류 질문과
꼬리질문을 합한 정확한 진행 상황이 표시됩니다. (confirmAnswer의 useCallback 의존성
배열에 queueIndex를 빠뜨리면 클로저가 오래된 값을 참조하는 버그가 생기므로 함께 추가.)

[2. 셀프 카메라 미리보기(SelfPreview)를 화면 밖으로 드래그하면 되찾을 수 없던 문제]
"크기조절이나 이동을 고려해달라"는 요청으로 코드를 다시 보니, 드래그 이동 시 왼쪽/위
방향만 화면 안으로 제한하고 오른쪽/아래 방향은 전혀 제한이 없어서, 사용자가 실수로
화면 밖으로 완전히 드래그해버리면 다시 화면에 돌아오게 할 방법이 전혀 없었습니다(리셋
버튼도 없었음). 좁은 화면일수록 이 문제가 발생하기 쉽습니다.
수정 (features/interview/components/SelfPreview.tsx):
- 드래그 이동과 모서리 크기조절 모두 부모(스테이지) 영역 안으로 실시간 clamp하도록 수정.
- 더블클릭으로, 또는 우측 상단의 작은 "↺" 되돌리기 버튼으로 위치·크기를 기본값으로
  즉시 되돌릴 수 있게 추가.
- 좁은 화면(창 너비 480px 미만)에서는 기본 크기를 220×150 → 150×104로 더 작게 시작하도록
  변경.
※ 이 자동화 환경은 포인터 캡처 기반 드래그(setPointerCapture)를 프로그래밍적으로
재현하는 것이 안 돼서(합성 PointerEvent와 실제 마우스 드래그 둘 다 시도했으나 React
핸들러가 반응하지 않음) 실제 드래그 동작 자체는 자동으로 검증하지 못했습니다 — clamp
공식은 손으로 계산을 검증했고, 실제 드래그 확인은 사용자가 직접 해주시는 것이 정확합니다.

더 엄격하게 거부하는 경우가 있었습니다.

다시 나면 EMAIL_DOMAIN을 또 바꿔야 할 수 있다는 점을 SETUP.md에 메모해뒀습니다.

[2. 대화창(전사) 내용을 키보드로 완전히 지울 수 없던 버그]
"대화창 내용은 키보드로 지울 수 있게 해주고" 요청으로 코드를 보니, TranscriptPanel.tsx가
항상 transcript || interimTranscript를 화면에 보여주고 있었습니다 — 즉 사용자가 내용을
전부 지워서 빈 문자열("")로 만들어도, 화면은 아직 남아있는 interimTranscript(마이크가
직전에 인식했던 값)로 다시 채워져서 실제로는 절대 완전히 비울 수 없었습니다.
수정: 마이크가 실제로 듣고 있는 동안(isListening=true)에만 그 fallback을 쓰고, 그 외에는
transcript 값만 그대로 보여주도록 해서 빈 문자열도 정상적으로 유지되게 했습니다.

[3. 말이 끊길 때마다 자동으로 문장부호 추가]
"말이 끊길 때마다 마침표나 쉼표 등으로 끊어줘" 요청에 따라, useSpeechRecognition.ts의
onresult에서 인식 엔진이 "final"로 확정하는 구간(대체로 사용자가 잠깐 말을 쉰 지점)마다
끝에 일본어 마침표(。)를 자동으로 붙이도록 했습니다(이미 문장부호로 끝나면 건너뜀).
일본어 음성 인식은 문장부호를 거의 안 붙여주기 때문에 전사가 훨씬 읽기 편해지고, 문장
단위로 나누는 채점 로직(STAR 체크·정중체 비율 등)의 정확도도 함께 좋아집니다.

[4. 결과 화면에 질문별 답변 시간 + 목표 시간 비교 표시]
"모든 질문에 대한 답변 시간을 체크해달라"는 요청으로, 이미 서버에 저장되어 있던 질문별
duration_seconds를 결과 화면에 눈에 띄게 보여주도록 했습니다. 기존에는 카드 맨 아래
작은 회색 글씨에 초 단위로만 묻혀 있었는데, 이제 "답변 시간 75초 / 목표 60초"처럼
목표 시간과 나란히 보여주고, 목표의 1.3배를 넘으면 "길어요", 절반에 못 미치면 "짧아요",
그 사이면 "적당해요" 배지를 색깔로 구분해 붙였습니다(app/interview/result/[sessionId]/
page.tsx, app/globals.css의 .qa-duration-badge/.qa-duration-tag-*).

[1. 면접관 목소리 속도 조절 (+/-/기본값)]
"면접관 질문 속도가 느렸으면 좋겠는데, +/- 배속 기능을 질문 버튼 오른쪽에 넣어달라"는

0.5~1.4 범위, localStorage에 저장되어 다음 방문에도 유지)를 추가했습니다. 브라우저
기본 음성(utterance.rate)뿐 아니라 VOICEVOX 외부 음성(HTMLAudioElement.playbackRate)도
같은 배속이 적용됩니다. InterviewStage.tsx의 "다시 듣기 (TTS)" 버튼 오른쪽에 "− 0.95x
+" 컨트롤을 추가했고, 가운데 숫자 버튼을 누르면 기본값(0.95x)으로 즉시 되돌아갑니다.

[2. 면접관이 지금 읽고 있는 글자를 요미가나 점처럼 실시간 표시]
"질문하는 타이밍이 늦은데, 지금 읽는 부분을 요미가나처럼 점으로 표시해줄 수 있나" 요청에
따라, 브라우저 TTS의 SpeechSynthesisUtterance.onboundary 이벤트로 지금 낭독 중인 글자
위치를 추적해서(useSpeechSynthesis.ts의 speakingBoundary), 질문 문장 중 해당 글자만
초록색으로 강조하고 그 글자 바로 위에 작은 점을 얹어(요미가나 점 느낌) 보여주도록
했습니다(InterviewStage.tsx, app/globals.css의 .room-question-reading).
※ 한계: 이 boundary 이벤트는 브라우저 기본 음성에서만 제공됩니다. VOICEVOX(외부 음성,
mp3 파일 재생 방식)는 글자 단위 이벤트가 없어서 이 표시가 뜨지 않습니다 — 기본 음성으로
낭독할 때만 동작하는 기능이라는 점을 사용자가 참고해주시면 좋겠습니다.

[3. 실전 면접에서 말할 때 음성 파형(웨이브폼) 시각화 추가]

주파수 분석 라이브러리 없이(0원 운영 원칙), 막대 24개에 고정된 "기본 굵기"(사인파를
겹쳐서 미리 계산 — 참고 이미지처럼 덩어리진 모양이 나오도록)를 마이크 실시간 레벨과
곱해서 자연스러운 파형처럼 보이게 했습니다. "듣고 있습니다" 표시 바로 아래, 면접
화면(InterviewStage) 중앙에 항상 보이도록 배치했습니다.

  Annyang으로 바꿔도 인식 정확도나 속도는 전혀 달라지지 않고, API 표기 방식만 바뀝니다
  — 지금 훅(useSpeechRecognition.ts)이 이미 같은 브라우저 엔진을 직접 쓰고 있어서
  얻는 이득이 없다고 판단했습니다.
결론적으로 이번 요청은 "음성 파형 시각화(위 §3)"로 구현하고, STT 엔진 자체는 그대로
유지했습니다. 나중에 유료 서버 운영을 고려하게 되면 그때 다시 검토할 만한 옵션으로
남겨둡니다.

[2. 요청하신 주제로 대분류 질문 6개 신규 추가]

  "이 회사를 왜"이고 이건 "회사 고를 때 기준이 뭐냐"라 성격이 달라서 그룹으로 묶지
  않았습니다)

  "일본생활" (기존 adapt_japan_life와 같은 그룹)
- day_off_activity (personality): "休日はどのように過ごすことが多いですか。" — "취미"
  (기존 hobby와 같은 그룹)
- years_in_japan_career (culture_fit): "日本でのキャリアをどのくらいの期間続けたいと
  考えていますか。" — "일본에 언제까지 일하고 싶은지" (기존 years_in_japan과 같은 그룹.

"팀 프로젝트 경험"과 "학창시절 힘쓴 일"은 이미 대분류에 여러 개(team_project 및 꼬리질문

그룹만 매겼습니다.

[3. 비슷한 질문끼리 그룹핑 + 한 세션에 한 그룹당 하나만 무작위로 뽑기 (신규 메커니즘)]
"비슷한 질문이 나오면 안 되니까 묶어서 정리하고, 그 중에서 랜덤으로만 뽑게 해달라"는
요청으로, data/questions.json의 질문 스키마에 선택적 group 필드를 추가했습니다. 기존에
이미 있었던 사실상 중복 질문 쌍들도 이번에 찾아서 그룹으로 묶었습니다:
  stress_relief:      stress, stress_relief_method (스트레스 해소법 두 표현)
  school_effort:       effort_in_school_days, childhood_effort (학창/어린 시절 힘쓴 일)
  hobby:               hobby, day_off_activity (취미 / 휴일을 보내는 방법)
  japan_life_adapt:    adapt_japan_life, life_in_japan_experience (일본 생활 적응)
  japan_impression:    japan_impression, japan_like_point (일본 인상 / 좋아하는 점)
  years_in_japan:      years_in_japan, years_in_japan_career (일본 근무 희망 기간)

lib/questionBank.ts에 sampleMainQuestions(categories, poolSize) 함수를 새로 추가했습니다
— 후보 질문들을 group(없으면 자기 id)별로 묶고, 그룹을 무작위로 섞은 뒤 각 그룹에서 대표
질문 하나만(그룹 안에서도 무작위) 뽑아 세션 풀을 구성합니다. 즉 "스트레스를 어떻게

  · 답변에 "雰囲気"(분위기)/"ムードメーカー"/"盛り上げ"(분위기를 띄움)/"調整役"(조율
    역할)이 나오면 → tp_role_tier1(공식 역할 외에 분위기·소통 면에서 어떤 역할을

[3. "핵심 꼬리질문인데 키워드를 안 말하면 영영 못 물어본다"는 문제 완화]

단어를 안 쓰면, 팀 갈등 해결 능력을 물어보는 tp_conflict_tier1은 그 세션에서 절대 안 나옵니다.
두 가지 방법으로 완화했습니다.

(a) 안전망(*) 규칙 신규 지원: public/data/follow_ups.txt의 감지할단어 칸에 '*' 하나만 쓰면,
    다른 규칙이 전부 안 맞았을 때만 마지막으로 검사해서 50% 확률로라도 발동하는 규칙이 됩니다.
    lib/followUp.ts의 matchFollowUpRule은 원래부터 triggerType: 'random'을 지원하고 있었는데
    (전에는 안 쓰이던 기능), 텍스트 파일 형식에서 이걸 지정할 방법이 없어서 실제로는 한
    번도 활용되지 않고 있었습니다 — 이번에 lib/questionBank.ts의 parseFollowUpsText가 '*'를
    인식해서 triggerType: 'random'으로 파싱하도록 고쳐서 이 기능을 실제로 켰습니다. 우선순위를
    -1로 낮게 줘서, 진짜 키워드 매칭이 항상 먼저 시도되고 아무것도 안 걸렸을 때만 개입합니다.
    적용한 안전망 7개: team_project→tp_conflict_tier1, why_this_company→why_not_other_company,
    motivation→motiv_strength_tier1, problem_solving→how_solved,
    opinion_conflict_communication/conflict→opinion_split_decision,
    setback_experience/failure_experience_general→fail_cause_tier1.
    Node로 2000회 시뮬레이션해서 키워드 없이도 약 48%(≈50%) 확률로 발동하고, 진짜 키워드가
    있을 때는 항상 우선순위 높은 진짜 규칙이 먼저 발동하는 것을 확인했습니다.

(b) 대분류 질문을 꼬리질문으로 먼저 물어보고 나중 자리는 자동 제거: "자기소개에서 팀플
    얘기가 나오면, 그 자리에서 바로 team_project(대분류 질문)를 물어보고, 나중에 세션
    풀에서 또 뽑힐 수도 있는 team_project는 미리 없애자"는 사용자 제안을 그대로 구현했습니다.
    - 꼬리질문의 "다음질문"은 태그와 무관하게 id로만 연결되므로, 대분류 질문(team_project)도
      얼마든지 꼬리질문 대상으로 지정할 수 있다는 점을 활용해 follow_ups.txt에
      `self_intro | チーム,チームプロジェクト,協力,共同 | team_project | 1` 규칙을 추가했습니다.
    - features/interview/hooks/useInterviewMachine.ts의 confirmAnswer: 꼬리질문을 큐에
      끼워 넣기 직전에, 이후 순서에 같은 id가 이미 있으면 먼저 제거하도록 수정했습니다
      (`prev.filter(q => q.id !== followUpQuestion.id)` 후 splice) — 그래서 team_project가
      자기소개 직후 꼬리질문으로 나오면, 나중에 세션 풀에 예정되어 있던 자리는 자동으로
      사라지고 같은 질문이 두 번 나오지 않습니다. Node로 배열 시뮬레이션해서 중복이 정확히
      0번임을 확인했습니다.
    - 이 패턴(자기소개 → 특정 주제 즉시 파고들기)은 다른 주제로도 그대로 확장할 수 있습니다.
      다만 "꼬리질문의 키워드 없이도 더 깊은 단계(tier2/tier3)까지 억지로 계속 파고들자"는
      부분은 적용하지 않았습니다 — tier2/tier3 질문들은 "その対立/それ" 같은 대명사로 앞
      답변의 구체적 내용을 가리키는 문장이라, 실제로 그 내용이 언급된 적이 없는데 질문만
      먼저 던지면 앞뒤가 안 맞는 질문이 되기 때문입니다. tier1까지는 즉시 선점하되, 더
      깊은 단계는 여전히 실제로 그 키워드가 나왔을 때만 자연스럽게 이어지도록 유지했습니다.

[진단]
1. curl로 Supabase Auth REST API(`/auth/v1/signup`)를 직접 호출해 같은 도메인

   자체는 문제가 아니었습니다(voiceinterviewjp-users.com도 정상적인 이메일 형식으로
   받아들여짐).
2. `/auth/v1/settings`를 GET으로 조회해 실제 프로젝트 설정을 확인한 결과,
   `"mailer_autoconfirm": false` — 즉 **"Confirm email"(가입 확인 메일 요구) 설정이 아직
   켜져 있는 상태**였습니다. 이 앱의 고유 번호 로그인은 실제로 존재하지 않는 가짜 이메일
   주소를 쓰기 때문에, 이 설정이 켜져 있으면:
   - 회원가입할 때마다 실제로 확인 메일을 "발송 시도"하게 되고 (Supabase 무료 티어 내장
     메일러의 시간당 발송 한도가 매우 낮아 금방 위 rate limit에 걸림),
   - 설령 메일이 발송되어도 가짜 주소라 아무도 그 확인 링크를 클릭할 수 없어 계정이 영원히
     "미확인" 상태로 남고, 로그인이 완료되지 않습니다.
   이건 실제로 SETUP.md 9~18번째 줄과 55~63번째 줄에 이미 "반드시 꺼야 한다"고 문서화까지
   되어 있던 사전 준비 단계인데, 이 Supabase 프로젝트에서는 아직 실제로 꺼져 있지 않은
   상태였습니다 — 즉 **코드 버그가 아니라, 배포 전 필수 설정이 아직 적용 안 된 것**입니다.

고유 번호(debugcheck3)로 실제 로그인 → 연습 모드 시작 → 텍스트 모드로 질문 2개에 실제로

curl로 같은 insert를 직접 재현해 정확한 원인을 확정했습니다:
  {"code":"22P02","message":"invalid input syntax for type uuid: \"failure_in_development\""}

아직 uuid 타입**으로 되어 있었습니다(사용자가 맨 처음 프로젝트를 만들 때 실행한 구버전
schema.sql 그대로) — 그런데 지금 코드는 질문을 Supabase의 questions 테이블(uuid)이 아니라
data/questions.json의 문자열 slug(예: "failure_in_development", "team_project")로 관리하도록
이미 오래 전에 바뀌어서, 문자열을 uuid 컬럼에 넣으려다가 매번 실패하고 있었던 것입니다.
question_id를 아예 안 넣고 나머지 컬럼만 insert해보니 전부 정상 저장되는 것을 확인해서

filler_counts, feedback_result 등 전부 문제없음), 문제는 정확히 이 두 컬럼의 타입
불일치 하나뿐임을 확정했습니다.

**다행히 이 저장소 안에 정확히 이 문제를 고치는 1회성 마이그레이션 스크립트가 이미
준비되어 있었습니다(supabase/migrate_local_questions.sql, SETUP.md §1-2에도 안내됨).
사용자가 아직 실행하지 않았을 뿐입니다.**
